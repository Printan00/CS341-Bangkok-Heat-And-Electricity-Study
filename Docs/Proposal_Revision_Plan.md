## 2. รายละเอียดและร่างข้อความ

### จุดที่ 1 — ลำดับขั้นและ Zone ใน Architecture

**ปัญหา**
- รูปปัจจุบัน: Step Functions → TransformBatch → Validation → Valid?
- Module 05 สอน: Check → Validate → Transform → Verify (ข้อมูลที่ยังไม่ผ่านการตรวจไม่ควรถูกแปลงก่อน)
- มี Raw กับ Curated แต่ไม่มี Trusted (Module 03) และไม่มีขั้น Verify หลัง publish (Module 04: "รันสำเร็จ ≠ ข้อมูลถูกต้อง")

**ลำดับที่เสนอ**

```
Sources (Happy Home, SoVI V8, GEE*)
  → Ingest (AWS CLI/Python: บันทึก source, date, version)
  → S3 Raw (เก็บต้นฉบับ ไม่เขียนทับ)
  → CheckBatch (เคยประมวลผลแล้วหรือยัง: _SUCCESS marker → กัน duplicate)
  → Validate (schema/codebook, missing, duplicates, outliers, หน่วยเวลา)
        ├─ FAIL → Quarantine + report (เก็บไว้ตรวจสอบย้อนหลัง ไม่ลบ)
        └─ PASS ↓
  → Transform (จัดรูปตัวแปรร่วม, แปลงชนิดข้อมูล, ใช้รหัสครัวเรือนนามแฝง)
  → S3 Trusted (Parquet: โครงสร้างแล้ว + ตรวจแล้ว)
  → Integrate (เทียบระดับกลุ่มบนตัวแปรร่วม; GEE รวมระดับชุมชนเมื่อมีรหัสพื้นที่เพียงพอ)
  → S3 Curated (Parquet: ตารางวิเคราะห์ Q1–Q3 พร้อม lineage)
  → Verify (จำนวนแถว, ค่าว่างในฟิลด์บังคับ, schema, เทียบยอดรวมกับ Raw)
  → DuckDB + SQL → Amazon QuickSight
```
(*GEE เป็นทางเลือก ตัดได้ตามเงื่อนไขในจุดที่ 3)

**ข้อความอธิบายที่เพิ่มใต้รูป (ร่าง)**
> ข้อมูลที่ยังไม่ผ่านการตรวจสอบจะไม่ถูกแปลง: Validate ทำก่อน Transform หากไม่ผ่านจะถูกแยกไป Quarantine พร้อมรายงานเพื่อให้ตรวจย้อนหลังได้ Raw เก็บต้นฉบับไว้เสมอ Trusted คือข้อมูลที่ผ่านการตรวจและจัดโครงสร้างแล้ว Curated คือตารางที่จัดเพื่อตอบคำถาม ส่วน Verify ตรวจว่าผลลัพธ์ถูกต้องจริง ไม่ใช่เพียงรันสำเร็จ

**ข้อควรระวัง:** ถ้าตัดสินใจเรื่องรหัสนามแฝงไว้ที่ Transform ให้ทำก่อนเขียนลง Trusted เพื่อไม่ให้ข้อมูลระบุตัวตนไหลไป zone ที่ใช้ร่วมกัน

### จุดที่ 2 — ขั้น Integrate, Parquet และป้ายชื่อ

- เพิ่มกล่อง **Integrate** ระหว่าง Trusted กับ Curated (ดูลำดับด้านบน)
- ระบุ **Parquet** บนกล่อง Trusted และ Curated
- วาดรูปใหม่ที่ความละเอียดสูงพอ ป้ายเล็กๆ ที่อ่านไม่ออก (เช่น ป้ายข้างกล่อง Step Functions) ให้ขยายหรือลบ
- เส้นจาก GIS/GEE ให้ระบุว่าเป็นทางเลือกและเชื่อมระดับชุมชน (เส้นประ)
- ความสอดคล้องกับข้อความ: Proposal ระบุว่า "ไม่เชื่อมสองชุดสำรวจที่ระดับครัวเรือน" ดังนั้นกล่อง Integrate ต้องแสดงว่าเป็นการเทียบระดับกลุ่ม ไม่ใช่ join ราย ID

### จุดที่ 3 — Design Decisions (alternatives → choice → reason / trade-off)

**Decision 1 — Transformation Rule: จะนำ GEE (อุณหภูมิพื้นผิว) มาเสริมข้อมูลสำรวจหรือไม่**

| ส่วน | ร่างข้อความ |
|---|---|
| Requirement | SoVI V8 ไม่มีตัวแปรความร้อนในบ้านโดยตรง แต่ CLD ต้องการดูความร้อนที่ครัวเรือนได้รับ |
| Alternatives | (A) ไม่ใช้ GEE วิเคราะห์เฉพาะข้อมูลสำรวจ (B) รวมค่า LST เป็นระดับชุมชน แล้วเทียบกับผลสำรวจระดับกลุ่ม (C) join ค่า LST เข้าครัวเรือนรายหลัง |
| Choice | B แบบมีเงื่อนไข; ตัด C; ถ้าเงื่อนไขไม่ผ่านจะถอยเป็น A |
| Reason | C ทำไม่ได้/ไม่ควร เพราะ LST ความละเอียดประมาณ 30 ม. (Landsat 8) และไม่มีพิกัดครัวเรือนที่เปิดเผยได้ และเสี่ยง MAUP/ecological fallacy (ตามสไลด์ GeoAI) การใช้ระดับชุมชนจึงตรงกับความละเอียดของข้อมูลมากกว่า |
| Trade-off | ได้บริบทความร้อนเชิงพื้นที่ แต่ LST ≠ อุณหภูมิในบ้าน ผลวิเคราะห์เป็นระดับกลุ่ม และเพิ่มงานจัดการ CRS/เวลา; **เงื่อนไขตัดทิ้ง** = ไม่มีรหัสพื้นที่/ช่วงเวลาเพียงพอ (ตรงกับ S3) |

**Decision 2 — Serving: เลือก Amazon QuickSight หรือไม่ และใช้ AWS กับข้อมูลขนาดเล็กอย่างไร**

| ส่วน | ร่างข้อความ |
|---|---|
| Requirement | แสดงผลวิเคราะห์ Q1/Q2 ให้ผู้นำชุมชนและอาจารย์ดูได้ โดยลดงานดูแลระบบ |
| Alternatives | (A) DuckDB + SQL + notebook/รายงานอย่างเดียว (B) Athena + QuickSight (C) dashboard แบบ self-host (เช่น Streamlit/Metabase) (D) DuckDB บน Parquet ใน S3 + QuickSight |
| Choice | D: วิเคราะห์ด้วย DuckDB/SQL บน Parquet ใน Curated แล้ว QuickSight เป็นชั้นแสดงผล |
| Reason | ข้อมูลมีขนาดเล็ก (~81 และ ~500 ครัวเรือน) ถ้าดูเฉพาะขนาดข้อมูล DuckDB หรือ Pandas ก็เพียงพอ (ตรงกับที่ Module 07 ย้ำ: เลือก engine ตามขนาด) เราเลือกใช้ S3 + Terraform เพราะ pipeline ต้อง **รันซ้ำได้ มีหลักฐาน และควบคุมสิทธิ์ข้อมูลสำรวจ** ได้ (Module 03/05) ไม่ใช่เพราะข้อมูลใหญ่ |
| Trade-off | ได้ reproducibility, IAM และ dashboard สำเร็จรูป แต่ซับซ้อนและมีค่าใช้จ่ายมากกว่า (A)/(C) สำหรับข้อมูลระดับนี้; ต้องเทียบ **ค่า QuickSight กับงบ/สิทธิ์ใน Learner Lab** ก่อนยืนยัน; ถ้าไม่เหมาะสมให้ใช้ (C) หรือ (A) แทน |

> ตรวจสอบก่อนใส่ในไฟล์จริง: ข้อมูลค่าบริการและสิทธิ์ใช้งาน QuickSight ใน Learner Lab ต้องเช็กจริง ข้อความข้างต้นไม่ได้อ้างตัวเลขราคา

**แก้คำผิด:** "เรื่อบควาร้อน" → "เรื่องความร้อน", "Amazon Quicksight" → "Amazon QuickSight"

### จุดที่ 4 — หลักฐานงานวิจัยเดิมของ H1/H2

สเปกให้ระบุว่า "มีงานศึกษาหรือหลักฐานใดสนับสนุนอยู่แล้ว และส่วนใดยังเป็นสมมติฐาน" ตอนนี้ตารางมีแต่ "สมมติฐานว่า…"

**แนวทางเพิ่มคอลัมน์ (โครง)**

| Relationship | หลักฐานเดิม (อ้างอิง) | ส่วนที่ยังเป็นสมมติฐาน |
|---|---|---|
| H1 ลักษณะบ้าน/ร่มเงา/การระบายอากาศ → ผลกระทบจากความร้อน (−) | **TODO: ใส่ 1–2 แหล่ง** | ผลกระทบเป็นการรายงานเอง, ไม่มีการวัดอุณหภูมิในบ้าน, อาจปนกับน้ำท่วม |
| H2 การใช้เครื่องทำความเย็น → ค่าไฟ (+) | **TODO: ใส่ 1–2 แหล่ง** | ความสัมพันธ์ในกลุ่มตัวอย่างนี้ และยังไม่ทราบว่าแยกค่าไฟจากรายจ่ายรวมได้หรือไม่ |

- **ยังไม่ได้ใส่ชื่อบทความ** เพราะต้องเป็นแหล่งที่ตรวจสอบได้จริง ห้ามเดาหรือสร้างรายการอ้างอิง
- แนวทางหา: ถามอาจารย์แอนว่ามีงานวิจัยที่ใช้ข้อมูล SoVI/Happy Home อยู่แล้วหรือไม่ (น่าจะเป็นแหล่งแรกสุด), ค้นคำเช่น *urban heat vulnerability housing characteristics*, *residential cooling electricity energy burden income*, *Bangkok heat vulnerable households*
- แนะนำให้ผู้รับผิดชอบเปิดอ่านต้นฉบับและสรุปสั้นๆ ว่ารองรับประเด็นใด ก่อนใส่ลง Proposal

### จุดที่ 5 — CLD

- เพิ่มป้าย **H1** บนเส้นที่ตรวจ (ลักษณะบ้านและวัสดุ → ผลกระทบจากความร้อน ผ่านความร้อนในบ้าน) ให้สอดคล้องกับป้าย H2 ที่มีอยู่
- ตรวจให้เครื่องหมาย (+/−) ในรูปตรงกับตาราง H1/H2

### จุดที่ 6 — ความยาว

สเปกแนะนำ 3–4 หน้า ตอนนี้ 8 หน้า สามารถลดได้โดยย่อรูป CLD และ architecture ให้พอดีหน้า และบีบตาราง Data ให้กระชับ ไม่ใช่เกณฑ์บังคับ ถ้าเนื้อหาครบและอ่านง่ายอยู่แล้ว ไม่จำเป็นต้องตัด
