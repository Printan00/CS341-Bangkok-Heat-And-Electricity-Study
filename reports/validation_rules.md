แหล่งข้อมูล 3 แหล่ง: **Happy Home**, **SoVI V8** (ทดสอบกับ sample แล้ว) และ **Google Earth Engine / Landsat LST** (ยังไม่มีข้อมูล กฎใน §7 เป็นสัญญาที่กำหนดไว้ล่วงหน้า และใช้ก็ต่อเมื่อ #23 ตัดสินใจเก็บ GEE ไว้)

**ขอบเขต:** เอกสารนี้กำหนดว่าขั้น Validate จะตรวจอะไร ระดับความรุนแรงเท่าไร และแถวที่ไม่ผ่านจะไปไหน
**กฎความเป็นส่วนตัวของเอกสารนี้:** ใช้แบบเดียวกับ `data_dictionary.md` คือมีเฉพาะจำนวนรวม จำนวนที่น้อยกว่า 5 แสดงเป็น `<5` ไม่มีรหัสครัวเรือน ไม่มีพิกัด และไม่มีสถิติที่คำนวณจากพิกัด

## 1. สรุปผล

| ชุดข้อมูล | แถวเข้า | ผ่าน (ไป Transform) | Quarantine | มีธงเตือน (ผ่าน แต่ติด `dq_flags`) |
|---|---|---|---|---|
| Happy Home | 88 | **81** | **7** (ชื่อชุมชนจับคู่ไม่ได้) | 10 (ในจำนวนนี้ 7 แถวติด W01) |
| SoVI V8 | 500 | **500** | 0 | <5 ต่อกฎ |
| GEE (Landsat LST) | ยังไม่มีข้อมูล | – | – | – (ดู §7) |

ข้อค้นพบหลัก:
1. **7 แถวใน Happy Home ที่ชื่อชุมชนเป็นอักขระเดี่ยวหรืออ่านไม่ออก** ไม่ใช่แค่ข้อมูลสกปรก ทั้ง 7 แถวตอบข้อ B13 ซึ่งเป็นคำถาม **[เฉพาะชุมชนมิตรประชา]** และแถวที่พิกัดว่างหรืออยู่นอกกรุงเทพฯ ก็อยู่ในกลุ่มนี้ทั้งหมด จึงอาจเป็น**ชุมชนที่ 3** (มิตรประชา/บ้านมั่นคง) ไม่ใช่คนรักถิ่นหรือหลังแฟลต
2. **88 − 7 = 81** ตรงกับตัวเลข "~81 ครัวเรือน" ที่ประกาศไว้พอดี (**เป็นสมมติฐาน** ต้องถามอาจารย์ยืนยัน)
3. นอกจากเรื่องชุมชน ข้อมูลทั้งสองชุดสะอาดมาก: id ไม่ซ้ำ, flag ของข้อที่ตอบได้หลายข้อตรงกับข้อความ 100%, skip logic ถูกต้อง, ไม่มีแถวว่างหรือแถวซ้ำ
4. แผนเดิมใน `data_dictionary.md` ที่ให้ "แก้ชื่อชุมชนด้วยพิกัด" **ทำไม่ได้** เพราะแถวที่จับคู่ชื่อไม่ได้คือแถวที่พิกัดใช้ไม่ได้ด้วย

## 2. หลักการออกแบบ

- **ตรวจ 3 ระดับ:** Batch (ทั้งไฟล์) → Row (รายแถว) → Column (รายคอลัมน์)
- **ระดับความรุนแรง 3 ระดับ**

| Severity | ผล |
|---|---|
| `FAIL` | Batch: หยุดทั้ง batch / Row: แถวไป Quarantine พร้อมเหตุผล |
| `WARN` | แถวผ่านไป Transform แต่ติดธงในคอลัมน์ `dq_flags` (list ของ rule_id) ให้การวิเคราะห์เลือกได้ว่าจะตัดหรือไม่ |
| `INFO` | บันทึกในรายงานเท่านั้น |

- **ไม่แก้ข้อมูลด้วยมือ:** การแก้ทำผ่าน "ไฟล์สัญญา" (contract) เช่น ตาราง mapping ชื่อชุมชน แล้วรัน validate ใหม่ แถวใน quarantine จะกลับมาผ่านเองเมื่อกฎเปลี่ยน
- **Normalise ก่อนตรวจ:** ทำแค่ตัดช่องว่างหัวท้าย แปลง `-` เป็น `–` (en dash) และใน SoVI แปลงค่า `-` ในช่องจำนวนคนเป็น 0 การเปลี่ยนความหมายของข้อมูลเป็นงานของขั้น Transform
- **ห้ามสร้างชุดค่าที่ถูกต้องจากข้อมูลที่เห็น:** ถ้าเอาค่าจาก sample มาเป็นชุดค่าที่ยอมรับ ทุกแถวจะผ่านเสมอและกฎจะไม่มีวันจับ batch ใหม่ได้ ต้องเอามาจากแบบสอบถาม `.docx` และชีต `ค่าคะแนน`

> **เงื่อนไข:** ใช้ส่วนนี้ก็ต่อเมื่อ #23 ตัดสินใจเก็บ GEE ไว้ (Proposal Decision 1 ทางเลือก B: รวม LST เป็นระดับชุมชน แล้วเทียบกับผลสำรวจระดับกลุ่ม) **ยังไม่มีไฟล์ GEE จึงยังไม่ได้ทดสอบกฎ** คอลัมน์ "ข้อมูลทดสอบ" ระบุข้อมูลผิดที่ตั้งใจสร้างขึ้นเพื่อพิสูจน์ว่ากฎทำงานจริง (ตาม Done criteria ของ #19)

**ตาราง `community_key` ใช้ร่วมกันทั้ง 3 แหล่ง:** ตาราง mapping ของ R03 (HH) และรายชื่อชุมชนของ S02 (SoVI) คือตารางเดียวกับที่ใช้ตรวจแถว GEE
- SoVI "ชุมชนขนาดเล็ก (รวม)" ระบุตำแหน่งไม่ได้ จึงไม่นำไปเชื่อมกับ GEE (INFO)
- SoVI หาตำแหน่งได้จากชื่อชุมชนเท่านั้น เพราะยังไม่รู้ความหมายของรหัส `(NN)`

### 7.2 กฎความเป็นส่วนตัวของ geometry (สำคัญที่สุด)

ขอบเขตชุมชนที่ส่งเข้า GEE จะถูกอัปโหลดไปที่ Google จึงต้องเป็นไปตามนี้
- **ต้องมาจากแหล่งสาธารณะเท่านั้น** เช่น แผนที่สาธารณะ ขอบเขตแขวง/เขต หรือ polygon ที่วาดเองรอบตำแหน่งชุมชนที่รู้กันทั่วไป
- **ห้ามสร้างจากพิกัดครัวเรือน** ไม่ว่าจะเป็น centroid, convex hull หรือ buffer รอบบ้าน และห้ามอัปโหลดจุดครัวเรือนเป็น asset เพราะ polygon ที่วาดรอบบ้านเปิดเผยตำแหน่งบ้านได้
- ใช้พิกัด HH ได้แค่**ในเครื่อง** เพื่อเช็กว่า polygon สาธารณะครอบคลุมบ้านในชุมชนนั้นจริง (G-W03) และรายงานเป็นจำนวนรวมพร้อมกฎ `<5`
- **พื้นที่ของ LST grid (b)** ต้องเป็นสี่เหลี่ยมหรือ polygon สาธารณะ เช่น ขอบเขตเขต หรือ buffer รอบ polygon ชุมชนสาธารณะ และต้องเป็นช่องสม่ำเสมอเต็มพื้นที่ **ห้ามเลือก ตัด หรือกรองช่อง grid ตามตำแหน่งบ้าน** (เช่น เก็บเฉพาะช่องที่มีบ้านอยู่) เพราะแผนที่จะเผยตำแหน่งบ้านทันที
- **บนแผนที่ QuickSight ห้ามมีจุดครัวเรือน** ไม่ว่าจะปัดพิกัดแล้วหรือไม่ (ตาม README: QuickSight เห็นเฉพาะตารางสรุปกลุ่ม n ≥ 5)

### 7.6 การแสดงผลใน QuickSight (heatmap) และสิ่งที่ Verify (#22) ต้องเช็ก

**แบบที่เสนอ:** ใช้ visual **Layer map** ไม่ใช้ Points on map เพราะ Points on map ระบายสีได้เฉพาะค่าที่เป็นหมวดหมู่ (ต้องตัด LST เป็นช่วง) ส่วน Layer map อัปโหลด GeoJSON ได้ (≤ 100 MB) จับคู่กับ dataset ด้วย key และไล่สีตามค่าได้ (gradient)
- **ชั้นที่ 1 heatmap:** `lst_grid_<survey>.geojson` จับกับตาราง curated ของ (b) ด้วย `cell_id` ระบายสีตาม `lst_median_c`
- **ชั้นที่ 2 ชุมชน:** polygon ชุมชนสาธารณะ จับกับตารางสรุปผลสำรวจรายชุมชนด้วย `community_key` เช่น % ครัวเรือนที่รายได้กระทบจากความร้อนมาก (D1.1), % มีแอร์ หรือคะแนน SoVI
- ภาพ visual ชื่อ "Heat map" ใน QuickSight เป็นตาราง แถว × คอลัมน์ ไม่ใช่แผนที่ อย่าเลือกตัวนี้

**ยังไม่ได้ยืนยัน (ต้องทดลองใน console):** ใส่ 2 ชั้นใน visual เดียวได้ไหม, Layer map ใช้ได้ใน `ap-southeast-1` ไหม, และการ join กับ dataset จาก Athena ทำงานอย่างไร

**สิ่งที่ Verify ต้องเช็กก่อนเขียน `_SUCCESS.json`** (ไม่ใช่กฎของ Validate)
| ตรวจอะไร | เหตุผล |
|---|---|
| GeoJSON ถูกต้อง เรียงพิกัดเป็น lon, lat (กรุงเทพฯ lon ≈ 100, lat ≈ 13–14 ถ้าสลับจะเห็นทันที) และไฟล์ ≤ 100 MB | ข้อจำกัดของ Layer map |
| key ตรงกัน 1:1 ระหว่างไฟล์ shape กับตาราง curated (`cell_id`, `community_key`) | key ที่ไม่ตรงจะ**ไม่แสดงบนแผนที่โดยไม่มี error** |
| ค่าสำรวจบนชั้นชุมชนเป็น null เมื่อ n < 5 | กฎ n ≥ 5 ของ README |
| ไม่มีคอลัมน์ lat/lon ระดับครัวเรือนใน dataset ที่ QuickSight อ่าน | กันจุดครัวเรือนหลุดขึ้นแผนที่ |

**ข้อสังเกตเรื่องความคุ้มค่า (ส่งต่อ #23):**
- **HH:** แผนที่จะมีแค่ 2–3 polygon ชุมชนในพื้นที่ประมาณ 4×4 กม. heatmap จะเล่าเรื่องได้น้อย
- **SoVI:** มีประมาณ 16 ชุมชนที่หาตำแหน่งได้ กระจายทั่วกรุงเทพฯ และปริมณฑล แต่ละชุมชนมีคะแนนความเปราะบาง จึงเหมาะกับการซ้อนบน LST มากกว่า แม้ SoVI ไม่มีตัวแปรความร้อนเอง
- **ปีไม่ตรงกัน:** SoVI ใช้ LST ปี 2023 แต่ HH ใช้ปี 2026 ต้องมีตัวกรองช่วงเวลา และใช้ชั้น LST ร่วมกันไม่ได้

### 7.7 ข้อจำกัดที่ต้องเขียนในรายงาน (ไม่ใช่กฎ)
- **LST ≠ อุณหภูมิในบ้าน** เป็นอุณหภูมิพื้นผิวตอนดาวเทียมผ่านช่วงสาย
- **HH มีแค่ 2–3 ชุมชนในพื้นที่ประมาณ 4×4 กม.** ความต่างของ LST ระหว่างชุมชนน่าจะน้อย และ n = 2–3 ทำสถิติไม่ได้ ให้รายงานเชิงพรรณนาเท่านั้น
- **MAUP / ecological fallacy:** ผลระดับชุมชนห้ามนำไปสรุประดับครัวเรือน
- ช่วงเวลา LST กับเวลาสัมภาษณ์ไม่ตรงกัน (HH สัมภาษณ์ ก.ค. 2026 แต่ถามความร้อนช่วงหน้าร้อนจากความจำ)
- ไฟล์ GEE ไม่มีข้อมูลส่วนบุคคล (ถ้าผ่าน G-B01) จึงเข้า pipeline ทาง `raw/gee/` เหมือนแหล่งอื่นได้ (ยังไม่ได้ทำ)

```
  rows.jsonl       แถวดิบที่ไม่ผ่าน (ทั้งแถว) + rule_ids
  manifest.json    id ที่ผ่าน (+ dq_flags, community_key) และ id ที่ไม่ผ่าน ให้ Transform (#20) ใช้คู่กับไฟล์ใน raw/
```
- ถ้าไม่ผ่าน privacy gate (B01) หรือหยุดที่ระดับ batch จะเขียนแค่ `dq_report.json` ไม่เก็บแถวใดๆ
- Validate **ไม่เขียน trusted/** เพราะแถวที่ผ่านยังมีพิกัดและยังไม่ได้แปลง (เป็นงานของ Transform)
- Lineage อยู่ใน `dq_report.json` / `manifest.json` (`batch_id`, `raw_key`, `source_sha256`) ส่วน `rule_version` ยังไม่ได้ทำ
- `quarantine/` สิทธิ์เข้าถึงจำกัดตาม IAM ของ Lambda และ bucket เปิด versioning ไม่ลบทิ้ง

### การปล่อยแถวออกจาก Quarantine
ไม่แก้แถวด้วยมือ ให้แก้ contract (เช่น เพิ่มชุมชนที่ 3 ในตาราง mapping) แล้วรัน pipeline ของ batch นั้นใหม่ แถวจะผ่านตามกฎใหม่

## 11. โค้ด

  - `xlsx.py` อ่าน .xlsx ด้วย `zipfile` + `xml` / `core.py` กฎระดับ batch, การแยกแถว, รายงาน
  - `happy_home.py`, `sovi.py` กฎรายแถว / `contracts/*.json` ข้อมูลอ้างอิง (คอลัมน์, ชุดค่าจาก .docx, mapping ชุมชน)

  - `BHES_SAMPLE_DIR=<โฟลเดอร์ไฟล์ sample> python -m pytest tests` ทดสอบกับไฟล์จริงด้วย (ใส่ค่าผิดลงในสำเนาแล้วต้องตกไป quarantine)

## 12. คำถามที่ต้องตัดสินใจหรือถามอาจารย์

1. **7 แถวที่จับคู่ชุมชนไม่ได้เป็นชุมชนมิตรประชาหรือไม่** ถ้าใช่ จะเพิ่มเป็นกลุ่มที่ 3 (n=7 เล็กมาก ต้องระวังกฎ <5 ในตารางไขว้) หรือตัดออกตามตัวเลข ~81 ที่ประกาศไว้
2. เกณฑ์ quarantine ทั้ง batch ใช้ 10% ไหม
3. ใน SoVI คะแนน 0 แปลว่า "ไม่เกี่ยวข้อง/ข้ามข้อ" ใช่หรือไม่ (ชีต key มีแค่ 1–3)
4. รหัส `(NN)` หน้าชื่อชุมชน SoVI คืออะไร
5. แถวที่ติด W01 (รายได้ต่ำสุดแต่ค่าไฟสูงสุด 7 แถว) จะตัดออกจากการวิเคราะห์ Q2 หรือรายงานทั้งแบบมีและไม่มีแถวเหล่านี้
6. **(GEE) #23 จะเก็บ GEE ไว้หรือตัดออก** ถ้าเก็บ ต้องกำหนด N (จำนวนชุมชน SoVI ขั้นต่ำใน G-B04)
7. **(GEE) ถ้า 7 แถวเป็นชุมชนมิตรประชาจริง** ต้องหา polygon สาธารณะของชุมชนนี้เพิ่มไหม

10. **(GEE/QuickSight) แผนที่หลักจะใช้ข้อมูลชุดไหน:** SoVI (~16 ชุมชน กระจายทั่วพื้นที่) หรือ HH (2–3 ชุมชน) หรือทำทั้งสองแผนที่แยกตามปี
