# Pipeline ของ GEE: อุณหภูมิพื้นผิว (LST) ระดับชุมชนและรายครัวเรือน

สถานะ: **รันบน AWS แล้วทั้งระดับชุมชนและรายครัวเรือน (23 พ.ย. 2026)** ผลอยู่ในหัวข้อ 8 · ต่อจาก [integration_feasibility.md](integration_feasibility.md) ข้อ 4 และ [risk_score_formulas.md](risk_score_formulas.md) หัวข้อ 4.3 (D14)

> กฎความเป็นส่วนตัว: พิกัดครัวเรือนอ่านในเครื่องเท่านั้น ไม่ขึ้น S3 ไม่อยู่ในไฟล์ที่ commit แหล่ง `gee_lst` มี 1 แถวต่อชุมชน แหล่ง `gee_lst_household` มี 1 แถวต่อครัวเรือน (มีแค่ `household_code` นามแฝงกับค่า LST ไม่มีพิกัดหรือชื่อชุมชน) **ห้ามนำค่า LST รายบ้านลงไฟล์ใน `reports/`** (repo เป็น public) ใช้ได้เฉพาะค่าสรุปที่ n ≥ 5

## สรุป

LST จาก Landsat 8/9 เข้า pipeline เป็น 2 แหล่งข้อมูล ใช้ state machine เดิม (CheckBatch → Validate → Transform → Integrate → Verify)

| แหล่ง | แถวละ | ตารางที่ publish | join เข้า `happy_home_risk` ด้วย |
| --- | --- | --- | --- |
| `gee_lst` | ชุมชน (รัศมี 300 ม. รอบกลางชุมชน) | `curated/community_dim/` | `community_key` |
| `gee_lst_household` | ครัวเรือน (รัศมี 50 ม. รอบจุดของบ้าน) | `curated/household_lst/` | `household_code` |

| คอลัมน์ใน `happy_home_risk` | ความหมาย |
| --- | --- |
| `lst_mean_c`, `lst_score`, `lst_batch_id` | LST ของชุมชนของบ้านหลังนั้น (°C), สเกล 30–45 °C → 0–1, batch ที่มา |
| `lst_hh_c`, `lst_hh_score`, `lst_hh_batch_id` | LST ที่จุดของบ้านหลังนั้น (°C, ปัด 0.1), สเกลเดียวกัน, batch ที่มา (D25) |

**LST ยังไม่อยู่ใน `risk_score`** (D21) เป็นตัวชี้วัดแยกตามขั้นที่ 4 ของ risk_score_formulas.md หัวข้อ 10 ข้อมูลรอบนี้มี 2 ชุมชน LST จึงมีแค่ 2 ค่า ทุกบ้านในชุมชนเดียวกันได้ค่าเท่ากัน ถ้าใส่ในสูตรจะเท่ากับบวกค่าคงที่ให้ทั้งชุมชน (ต่างกันราว 1.4 °C ≈ 0.09 บนสเกล 0–1) ควรดูความสัมพันธ์กับหมวดอื่นก่อน ค่ารายครัวเรือนก็ยังไม่อยู่ใน `risk_score` เช่นกัน

## 1. ลำดับขั้น

```
[เครื่องของทีม] scripts/gee_lst.py ──► data/gee_lst_community.csv   (1 แถว/ชุมชน ไม่มีพิกัด)
                                  └──► data/gee_lst_household.csv   (1 แถว/บ้าน: household_code + LST)
                scripts/ingest.py  ──► raw/gee_lst/<batch_id>/  และ  raw/gee_lst_household/<batch_id>/
[AWS] แต่ละแหล่ง: CheckBatch → Validate (G01–G10) → Transform → trusted/<source>/batch_id=<id>/
      → Integrate → staging → Verify → curated/community_dim/  หรือ  curated/household_lst/
[AWS] batch Happy Home: Integrate อ่านทั้งสองตารางที่ publish แล้ว → happy_home_risk.lst_* และ lst_hh_*
```

ทำไมดึงจาก Earth Engine ในเครื่อง ไม่ใช่ใน Lambda: การหาค่ากลางชุมชนต้องใช้พิกัดบ้าน ซึ่งห้ามขึ้น S3 (README หลักการออกแบบ) ถ้าดึงใน Lambda ต้องเก็บพิกัด (อย่างน้อยค่ากลางชุมชน) ไว้ใน AWS และต้องมี service account ของ Earth Engine ใน Lambda ด้วย งานนี้รันปีละไม่กี่ครั้ง การรันในเครื่องแล้ว ingest เฉพาะค่าสรุปจึงง่ายและปลอดภัยกว่า

**ลำดับการรัน:** รัน batch `gee_lst` และ `gee_lst_household` ก่อน (ลำดับระหว่างสองตัวนี้ไม่สำคัญ) แล้วจึงรัน Happy Home ถ้ามี batch GEE ใหม่หลังจาก Happy Home publish แล้ว ให้รัน Happy Home ซ้ำด้วย `{"batch_id": "<happy_home batch>", "force": true}` เพราะ CheckBatch จะข้าม batch เดิม ถ้ายังไม่เคยมี `community_dim` ระบบก็ยังรัน Happy Home ได้ตามปกติ แต่คอลัมน์ LST ของแหล่งที่ยังไม่มีจะเป็น null

สคริปต์ใช้ชื่อชุมชนตาม `community_map` ชุดเดียวกับ Validate (T04) ค่ากลางของชุมชนจึงคิดจากบ้านชุดเดียวกับที่จะได้รับค่า LST ใน `happy_home_risk` (แต่เดิมสคริปต์จับคำว่า "รักถิ่น"/"แฟลต" เอง ซึ่งอาจนับบ้านไม่ตรงกับ pipeline)

## 3. กฎ Validate (G01–G10)

อยู่ใน `lambdas/validate/gee_rules.py` ใช้ร่วมกันทั้งสองแหล่ง ต่างกันแค่คีย์ (`community` / `household_code`) ค่าเกณฑ์อยู่ใน `lambdas/common/contracts/gee_lst.json` (ช่วงที่เป็นไปได้และสเกลใช้ชุดเดียวกัน) และ `gee_lst_household.json` (คอลัมน์) ผลเขียนที่ `quarantine/<source>/<batch_id>/` เหมือน Happy Home แหล่งระดับชุมชนไม่ซ่อนจำนวน `<5` เพราะแต่ละแถวเป็นชุมชน แหล่งรายครัวเรือนซ่อนเหมือน Happy Home

| กฎ | ระดับ | ตรวจอะไร |
| --- | --- | --- |
| G01 | batch FAIL | อ่านเป็น CSV (UTF-8) ได้ |
| G02 | batch FAIL | มีคอลัมน์ที่ต้องมีครบ |
| G03 | batch FAIL | ไม่มีคอลัมน์ต้องห้าม: พิกัด (ทั้งสองแหล่ง), รหัสบ้าน (ระดับชุมชน), ชื่อชุมชน (รายบ้าน) ถ้ามีจะไม่เก็บแถวใดลง `rows.jsonl` เลย |
| G04 | แถว FAIL | คีย์ใช้ได้: ชุมชนเป็นค่าใน `community_map` / `household_code` ไม่ว่าง |
| G05 | แถว FAIL | คีย์ซ้ำ (แยกทุกแถวที่ซ้ำ) |
| G06 | แถว FAIL | `lst_mean_c` เป็นตัวเลขในช่วงที่เป็นไปได้ 15–70 °C (ช่วงตรวจความผิดพลาด ไม่ใช่ช่วงให้คะแนน) |
| G07 | แถว FAIL | `n_scenes` เป็นจำนวนเต็ม ≥ 1 |
| G08 | แถว FAIL | `period` ถูกรูปแบบและวันเริ่ม < วันจบ, `buffer_m` > 0, `source` ไม่ว่าง |
| G09 | batch FAIL | ทุกแถวที่ผ่านใช้ช่วงภาพ รัศมี และแหล่งภาพเดียวกัน (ไม่อย่างนั้นเทียบกันไม่ได้) |
| G10 | batch WARN | (ระดับชุมชนเท่านั้น) มีชุมชนของ Happy Home ที่ไม่มีแถว (บ้านในชุมชนนั้นจะได้ LST เป็น null) |

ระดับรายบ้านไม่ตรวจว่า `household_code` มีอยู่ใน Happy Home ตอน Validate เพราะสองแหล่งเป็นคนละ batch แถวที่ไม่ตรงกับบ้านใดจะไม่ถูกใช้ตอน join และ `_SUCCESS.json` ของ Happy Home บันทึก `lst_hh_households` (จำนวนบ้านที่ได้ค่า) ไว้ให้ตรวจ

batch ผ่าน (`valid`) เมื่อไม่มี batch FAIL และมีแถวผ่านอย่างน้อย 1 แถว

## 4. ตาราง

| ตาราง | Contract | แถวละ | คอลัมน์ |
| --- | --- | --- | --- |
| `trusted/gee_lst/` | `trusted_gee_lst.json` | ชุมชน | `community_key`, `lst_mean_c`, `n_scenes`, `period_start`, `period_end`, `buffer_m`, `lst_source`, `batch_id`, `source_row` |
| `curated/community_dim/` | `curated_community_dim.json` | ชุมชน | เหมือน trusted + `lst_score` |
| `trusted/gee_lst_household/` | `trusted_gee_lst_household.json` | ครัวเรือน | `household_code` + คอลัมน์เดียวกับ `trusted/gee_lst/` |
| `curated/household_lst/` | `curated_household_lst.json` | ครัวเรือน | เหมือน trusted + `lst_score` |
| `curated/happy_home_risk/` | `curated_happy_home_risk.json` | ครัวเรือน | ของเดิม + `lst_mean_c`, `lst_score`, `lst_batch_id` (null เมื่อ `community_key = unknown`) + `lst_hh_c`, `lst_hh_score`, `lst_hh_batch_id` (null เมื่อบ้านไม่มีค่า) |

Glue crawler เดิมจับ `community_dim` และ `household_lst` เป็นตารางใหม่ได้เอง (หนึ่งโฟลเดอร์ต่อหนึ่งตารางใต้ `curated/`) IAM ของ Lambda ครอบคลุม `raw/*`, `trusted/*`, `curated/*` อยู่แล้ว ไม่ต้องแก้ Terraform

## 5. Verify

- batch `gee_lst` / `gee_lst_household`: จำนวนแถว raw = ผ่าน + ถูกแยก, ผ่าน = trusted = ตารางที่จะ publish, คีย์ตรงกันและไม่ซ้ำ, schema และ null ตาม contract, `lst_mean_c` อยู่ในช่วงที่เป็นไปได้, `lst_score` คิดซ้ำได้ตรง ผ่านครบจึง publish `curated/community_dim/` หรือ `curated/household_lst/` และเขียน `_SUCCESS.json`
- batch Happy Home (เพิ่มข้อ 7): ทุกบ้านมี `lst_mean_c`/`lst_score`/`lst_batch_id` ตรงกับแถว `community_dim` ที่ publish แล้วของชุมชนตน (null ทั้งหมดเมื่อไม่มี) ทุกบ้านมี `lst_hh_*` ตรงกับแถว `household_lst` ของตัวเอง (null เมื่อไม่มี) และคะแนนทั้งสองชุดตรงกับสเกล 30–45 °C ที่คิดซ้ำในโค้ดของ Verify เอง `_SUCCESS.json` บันทึก `lst_batch_ids`, `lst_hh_batch_ids` และ `lst_hh_households`

## 7. ข้อจำกัด

1. 2 ชุมชน → LST มีแค่ 2 ค่า ใช้เป็นบริบทได้ ใช้ประมาณความสัมพันธ์รายครัวเรือนไม่ได้ (integration_feasibility ข้อ 4)
2. ภาพเป็นหน้าร้อนช่วงเช้า (Landsat 8/9 ผ่านราว 10 โมง) ไม่ตรงเดือนสำรวจ (ก.ค.) และ LST คืออุณหภูมิพื้นผิว ไม่ใช่อุณหภูมิในบ้าน
3. `n_scenes` นับภาพที่ครอบคลุม ไม่ใช่ภาพที่ไม่ติดเมฆ
4. ระบบพิกัดของ Happy Home ยังสมมติเป็น WGS84
5. ช่วง 30–45 °C เป็นค่าที่ทีมเลือก ถ้าเปลี่ยนให้แก้ `lst_score_c` ใน `gee_lst.json` แล้วรันทั้ง `gee_lst` และ Happy Home ซ้ำด้วย `"force": true`
6. รันบน AWS แล้วทั้งสองระดับ (หัวข้อ 8) เทสต์อัตโนมัติ (`tests/test_gee.py`, `tests/test_gee_household.py`) รันกับ S3 จำลอง
7. ค่ารายบ้าน: band ความร้อนละเอียดจริง 100 ม. แต่รัศมี 50 ม. จึงเฉลี่ยพิกเซลที่ resample จากพิกเซลจริงเพียง 1–2 พิกเซล และ 85 บ้านอยู่บน 24 จุด บ้านในจุดเดียวกันได้ค่าเท่ากัน ความต่างระหว่างบ้านใกล้กันส่วนใหญ่จึงน่าจะเป็นสัญญาณรบกวนของภาพ ไม่ใช่ความต่างของความร้อนที่บ้านเจอจริง
8. ค่ารายบ้านละเอียด 0.1 °C ร่วมกับภาพ Landsat สาธารณะ อาจใช้ระบุตำแหน่งบ้านคร่าว ๆ (≈ 100 ม.) ได้ จึงเก็บไว้แค่ใน lake (trusted/curated) ห้ามนำค่ารายบ้านลง `reports/` หรือแดชบอร์ดสาธารณะ
